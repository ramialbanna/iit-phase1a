## 5. Design consequences to carry (for docs/26 v0.10 / docs/51 v0.3 — proposals, nothing adopted)
**Codex (rev 2): "mandatory lookup + local fencing" is NOT a complete fix and is not adopted.** Lookup and Add are separate operations: two senders can both observe absence and both send; a sender that has lost its local fence can still reach AppSheet afterwards; the destination does not enforce the fence. Same-key mutation therefore breaks the earlier "harmless late send" argument. The design amendment that addresses this is **docs/56 (AM5 draft)**, which enumerates the races and the residual that would need an owner's acceptance.
1. **No server-side duplicate protection can be assumed** from AppSheet's `Add` on this table (observed once). A pre-send existence check narrows the window for a duplicate send but cannot close it (see docs/56 §2).
2. **`duplicate_key` → replace with `accepted_existing`** (200, echoed row, counts unchanged, initial values re-stamped) in the classifier; `duplicate_ours` must be decided by **reading the row and comparing stored-payload fields**, never by the response.
3. **Open question for Codex/Rami (E-3′):** whether Add-on-existing-key with a **changed** payload overwrites supplied fields. If yes, a late sender with a *different* payload could silently corrupt a row — but IN-2 makes payloads identical, so the realistic exposure is (a) re-stamped initial values and (b) collisions with native rows (a native row whose key happened to equal a supplied iD would be *overwritten*, not protected — the namespace disjointness becomes a **correctness** requirement, not a convenience).
4. **C2 as specified in v0.17 cannot pass** ("AppSheet rejects"); the v0.17 "S2 must prove" item (b) should be re-stated as: "a second Add with the same key creates no second row **and** is detected locally; its side effects on the existing row are known and acceptable or prevented."
