# Migration 001 — foundation (schema `iit`)

Status: **local only, rev 4 — Codex ACCEPT 2026-10-28** (pre-application amendment, 28 Oct: D-2 measured; `BYPASSRLS` removed — it needs a superuser to create and Supabase's `postgres` is not one, so rev 3 would have failed at application).

## 0b. Rev 4 — D-2 measured on the live project (Base44 → Supabase), and the application blocker it exposed
**Measured by the Base44 assistant on 28 Oct 2026 (SELECTs only, project `fqxfrtfiysbuctcccudb`):** the Base44 Supabase integration authenticates with an OAuth token against the **Supabase Management API** and runs SQL through `POST /v1/projects/{ref}/database/query`, which executes as **`postgres`** (`current_user = session_user = postgres`; not superuser; `BYPASSRLS`; `CREATEROLE`). The read-only endpoint runs as `supabase_read_only_user`; PostgREST with the service key as `service_role` (not the app's path). The `iit` schema and roles do not exist there yet.

What this means, stated plainly:
1. **`GRANT iit_integration TO postgres` is not the answer.** `postgres` already owns everything it creates and can `SET ROLE` to any role it created; EXECUTE grants to `iit_integration` constrain the *browser* path (publishable keys, `anon`/`authenticated`) exactly as §2.2 intends, but they do not constrain the Base44 backend at all.
2. **The Base44 backend is the database owner-equivalent on this path** (direct table writes, DDL, history forgery, even `DROP SCHEMA`). §2.5 risk 3 ("attribution stays trusted, not proven") is therefore the operative risk for every Base44 write, not a corner case. Detection exists: a direct write records `exec_role = postgres`, `actor_kind = 'direct'`, `origin_role` NULL, while a function write records `exec_role = iit_owner` (T16b/T16c) — but detection is not prevention.
3. **Options for the owner (D-2 resolution):** (a) accept: the Base44 app is reviewed to call only `iit.*` functions, with the history evidence as the audit; (b) discipline: every Base44 SQL request runs `BEGIN; SET LOCAL ROLE iit_integration; SELECT iit.fn(...); COMMIT;` so accidental direct writes are denied by RLS — *defense in depth, not a boundary*, since `postgres` can omit it; (c) a narrower connection path: Base44 backend functions call PostgREST RPC with a dedicated JWT role (`GRANT iit_integration TO <that role>`), which cannot run DDL — a change to how the app connects. Recommendation: (c) if Base44 can hold a secret and call PostgREST from its backend functions; otherwise (a)+(b).
4. **Blocker fixed in rev 4:** `CREATE ROLE iit_integration NOLOGIN BYPASSRLS` requires a superuser (PostgreSQL rule), so 001 rev 3 cannot apply on Supabase. Rev 4 creates the role **without** `BYPASSRLS`; RLS with no policies now denies the role's direct table writes (T16d) — the better property. T16b now captures a direct edit by the login role (locally the superuser, on Supabase `postgres`).
5. **`tav_worker` (D-46):** the Worker needs its own login path (Hyperdrive / direct Postgres login granted `tav_worker`); the Management API is not it.
 Applied and tested on a fresh local Postgres 16 (`supabase/tests/run_local.sh` → `ALL 001 TESTS PASS`, 19 check blocks). Not applied to Supabase. For Codex review.

## 0a. Rev 3 — JSON enforcement bypasses (Codex)
| # | Bypass | Change | Control |
|---|---|---|---|
| 1 | A `true` leaf accepted objects/arrays (`{"vehicle":{"vin":{"accountNumber":"123"}}}` passed) | A leaf admits scalars only (string/number/boolean/null); any structure needs an explicit schema | T12i object under leaf, T12j array under leaf rejected; scalar leaves incl. null and an array-of-objects with a schema accepted (`hScalars`) |
| 2 | JSON `null` treated like SQL NULL (a NOT NULL body could store `'null'::jsonb`; empty schemas admitted it) | `enforce_json` distinguishes the two with `_column_is_sql_null(NEW, col)`: SQL NULL passes where the table allows it; JSON null and non-object bodies raise `STORAGE_POLICY` | T12k JSON-null observation, T12l array body, T12x-c JSON-null 3.1 body, T10j JSON-null snapshot rejected; SQL-NULL draft snapshot accepted |

**Seed rows and history.** Rows inserted by this migration *before* `attach_history` runs on their table (`roles`, `source_channels`, `required_fact_rules`, `material_fields`, `system_settings`, `json_schemas`) have **no creation history row**; the migration file itself is their baseline. Every later change is recorded. The T18 inventory proves trigger coverage, not that creation history exists for these seeds.

- `source_records.created_via = 'bridge'` and `work_items.kind IN ('id_collision','delivery_failed_manual','vin_validation_rejected','duplicate_row')` are vocabulary only; nothing creates them.
- `source_records.legacy_iid` is "NULL until known"; with no bridge it is set only by cutover/manual paths (future slice).
