## 2. Behaviour
**Order in each wrapper.** (1) `require_logistics_reader()` — raises 28000 on failure, so no IIT row is written (the
Logistics Worker records it); (2) correlation id; (3) input checks; on a refusal: one `denied` audit row and the fixed envelope
`{status:"denied", error_code, correlation_id}` — returned, not raised, so the row commits; (4) the STABLE read helper;
(5) one `ok` audit row and `{status:"ok", error_code:null, correlation_id, rows}`.

**Credential.** Originating role must be `iit_logistics_reader` (`CREDENTIAL_WRONG_ORIGIN` otherwise — owner SQL, `postgres`,
service paths, Base44 and Worker roles included). Claims must be a JSON object (`CREDENTIAL_NO_CLAIMS`), `role` must be the
string `iit_logistics_reader` (`CREDENTIAL_ROLE_MISMATCH`), `jti` present (`CREDENTIAL_NO_JTI`), a JSON string in canonical
lowercase UUIDv4 form (`CREDENTIAL_INVALID_JTI`), and absent from `iit.revoked_credentials` compared as
`lower(btrim(jti))` (`CREDENTIAL_REVOKED`). Errors carry the code only. The database checks form and revocation; fresh
generation of the `jti` is the Worker's guarantee (plan T17). `require_role` now refuses an `iit_logistics_reader` origin
(`CREDENTIAL_WRONG_ORIGIN`) and Logistics claims under any origin (`CREDENTIAL_ROLE_MISMATCH`); every Base44 path is unchanged.

**Correlation id.** Accepted only as canonical lowercase UUIDv4 and stored as given (`correlation_source = 'caller'`).
NULL/empty → `CORRELATION_MISSING`; anything else → `CORRELATION_INVALID`; both get a server `gen_random_uuid()` that is
stored (`'server'`) and returned. The rejected value is never stored or echoed. Correlation is checked before inputs.

**Input checks**, in order: NULL or empty array → `INPUT_EMPTY`; multi-dimensional → `INPUT_INVALID`; more than 500 elements
(VINs: 50) → `INPUT_TOO_LARGE`, judged on `cardinality()` before any element is read; any NULL element →
`INPUT_NULL_ELEMENT`; 3.1 ID empty after `btrim()` or longer than 64 → `INPUT_INVALID`; deal id not canonical lowercase UUID
text → `INPUT_INVALID`. `input_count` = `cardinality()` (0 for NULL).

**Rows** — one per input position, duplicates kept, input order, 1-based `ordinality`, named keys only:
- `logistics_resolve_31`: `ordinality, legacy_iid` (trimmed), `found, deal_id, link_status, source_status, kind`. `found` and
  `deal_id` only for a source record with `link_status = 'linked'` and a deal; an unlinked/conflict record answers
  `found = false`, `deal_id = null` with its statuses; an unknown iD answers all-null.
- `logistics_deal_summaries`: `ordinality, deal_id, found, deal_number, vin_normalized, year, make_text, model_text,
  purchase_price, dealer_sold_to, source_channel_name, intake_status, cancelled_at, final_closure_at, on_hold`. No parties,
  liens, titles, reports, audit detail, deposit, balance or stock number.
- `logistics_vin_candidates`: `ordinality, vin_normalized, valid, error_code, found, candidate_count, deal_id, deal_number,
  intake_status, audit_status, on_hold`. Normalization `upper(btrim())`, as `vehicles.vin_normalized`; exact match. Live
  candidate: `cancelled_at IS NULL AND final_closure_at IS NULL AND intake_status <> 'voided'`. `deal_id` and the status fields
  only when exactly one live candidate exists. A position whose normalized VIN is empty or longer than 32 characters answers
  `valid = false, error_code = 'INPUT_INVALID'` with every other field null and is not looked up.

**Audit row** (`iit.logistics_read_audit`): `id, at, function, credential_jti uuid, correlation_id uuid,
correlation_source, input_count, invalid_count, outcome ('ok'|'denied'), error_code` (fixed set). CHECKs: `ok` ⇔ no error
code; a server correlation id only with a denial; `invalid_count` only on `ok` and ≤ `input_count`. Append-only, retained
indefinitely for Phase 1 (Q8), not history-covered. Never a VIN, deal id, 3.1 ID, row content or caller text.

## 6. Production blockers (open)
- **Not applied**, and steps 3–5 above are separately gated.
- **Logistics Worker alignment** with this contract (D-4 correlation codes, D-6 linked-only resolution, D-7 status keys,
  D-8 per-position invalid VINs, no `stock_number`), and its T17 `jti`-generation test, must be in place before the credential
  is minted.
- **`source_records` is still empty** in IIT (no bridge, cutover or manual linking yet), so `logistics_resolve_31` will answer
  `found = false` for every iD until linking exists (plan F5). Not a defect; Logistics must run its unresolved-link workflow.
- **Platform roles** (`postgres`, `supabase_etl_admin`, `supabase_read_only_user`) can read `iit.logistics_read_audit` like
  every `iit` table through `pg_read_all_data` (V-3, accepted).
