# Migration 006 — dedicated PostgREST role for Base44 (D-2 option c)

Status: **local only, rev 4 — for Codex review** (rev 3 Codex ACCEPT 2026-10-28; Codex rev-1 P1: per-token revocation; P2: exact manifest assertion; rev-2 P1: enforcement bound to the originating role).

**Rev 4 (executor, same root cause as 001 rev 5).** The schema `USAGE`, function `EXECUTE`, table/sequence `REVOKE` and `ALTER DEFAULT PRIVILEGES` statements ran as the executor before `SET ROLE iit_owner`; as Supabase's non-superuser `postgres` (no inherited owner privileges) they fail with 42501 — reproduced locally at `GRANT USAGE ON SCHEMA iit TO iit_base44` once 001 was fixed. They now run after `SET ROLE iit_owner` (the later `SET ROLE` is removed, so the statements' order and content are otherwise unchanged). `CREATE ROLE iit_base44` and the `authenticator` grant stay with the executor: its automatic ADMIN on the role it created is what authorizes that grant, and `iit_owner` has none. Codex review of rev 4: the grant now states its options, `GRANT iit_base44 TO authenticator WITH ADMIN FALSE, INHERIT FALSE, SET TRUE`, so `authenticator` can `SET ROLE iit_base44` but never inherits its privileges or administers its membership, independent of `authenticator`'s own `INHERIT` attribute; Z1b2/Z1b3 and `deploy_executor_test.sql` X4 assert exactly those options (mutations SET FALSE, INHERIT TRUE, ADMIN TRUE each rejected). `createrole_self_grant` is pinned empty around the `CREATE ROLE` as in 001. Applied and tested on a fresh local Postgres 16 after 001–005 (`run_local.sh` → all earlier suites + `ALL 006 TESTS PASS` Z1–Z9). Not applied to Supabase. For Codex review together with `docs/d2-deployment-package.md`, which holds the manifest, screen mapping, PostgREST configuration, credential procedures and the application sequence.

## 1. What it creates
`iit_base44` (NOLOGIN, NOINHERIT) with `USAGE ON SCHEMA iit` and `EXECUTE` on exactly the 27 staff-facing functions of 001–005 (same set as `iit_integration`); `GRANT iit_base44 TO authenticator WITH ADMIN FALSE, INHERIT FALSE, SET TRUE` when that role exists (Supabase's PostgREST login role; the local runner now creates `authenticator` to mirror it); explicit `REVOKE ALL` on every table and sequence; `ALTER DEFAULT PRIVILEGES FOR ROLE iit_owner … REVOKE ALL ON FUNCTIONS FROM PUBLIC` so future functions are private until granted.

Rev 2 adds `iit.revoked_credentials(jti, revoked_at, reason)` (history-covered, no DELETE) and replaces `require_role()` with per-token revocation. Rev 3 (Codex P1) ties that enforcement to the **originating role** — `current_setting('role')`, the same signal `record_history.origin_role` records — instead of to the claims' own say-so: when the originating role is `iit_base44`, claims must exist (`CREDENTIAL_NO_CLAIMS`), `claims.role` must equal `iit_base44` (`CREDENTIAL_ROLE_MISMATCH`), and the `jti` must be present (`CREDENTIAL_NO_JTI`) and unrevoked (`CREDENTIAL_REVOKED`) — all SQLSTATE 28000; when the originating role is anything else but the claims name `iit_base44`, the call is refused as an identity mismatch; claim-less calls from other roles (Worker, owner SQL, local tests) are unchanged. Z6e now succeeds only with the credential's claims; Z9a–e prove the four refusal paths from a real `authenticator` login, from the owner session and from `iit_integration`.
