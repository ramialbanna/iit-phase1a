# Migration 006 — dedicated PostgREST role for Base44 (D-2 option c)

Status: **local only, rev 1.** Applied and tested on a fresh local Postgres 16 after 001–005 (`run_local.sh` → all earlier suites + `ALL 006 TESTS PASS` Z1–Z7). Not applied to Supabase. For Codex review together with `docs/d2-deployment-package.md`, which holds the manifest, screen mapping, PostgREST configuration, credential procedures and the application sequence.

## 1. What it creates
`iit_base44` (NOLOGIN, NOINHERIT) with `USAGE ON SCHEMA iit` and `EXECUTE` on exactly the 27 staff-facing functions of 001–005 (same set as `iit_integration`); `GRANT iit_base44 TO authenticator` when that role exists (Supabase's PostgREST login role; the local runner now creates `authenticator` to mirror it); explicit `REVOKE ALL` on every table and sequence; `ALTER DEFAULT PRIVILEGES FOR ROLE iit_owner … REVOKE ALL ON FUNCTIONS FROM PUBLIC` so future functions are private until granted.

## 2. Controls
Z1 role attributes, membership, schema usage, manifest size 27, no table/sequence privilege · Z2 approved RPC succeeds under `SET ROLE iit_base44`; role and actor checks inside still apply; attribution `iit_owner/iit_base44/user` · Z3 helpers and Worker functions denied · Z4 every table verb, sequence and DDL denied · Z5 anon/authenticated/tav_worker denied on every manifest function · Z6 from a real `authenticator` login: cannot become owner/worker/integration/postgres; approved RPC works; table read refused · Z7 005 Worker grants and the `iit_integration` manifest unchanged.

## 3. Not here
Schema exposure (Supabase API setting), the credential (JWT minted by the owner), Base44 secret storage, migration application — all in the package §7, each requiring separate authorization. Read RPCs for the screens: **migration 007** (package §2).
